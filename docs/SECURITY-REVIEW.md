# Security review — 2026-10-18

The latest independent review covers [Fo execution and credential handoff](FO-FLOW-REVIEW.md). Earlier boundary findings are preserved in [Fo Reach version 4 review](REVIEW-2026-10-18.md).

## Bearer compatibility correction

The previous mandatory external-OAuth prerequisite was not supported by live Fo evidence. The parent now confirmed Fo's explicit bearer registration and post-registration `{token}` credential form, and OAuth's curated-provider/DCR requirement. An issuer URL alone is insufficient. The code preserves optional OAuth but adds a bounded single-owner bearer profile with separate configured digests, a deadline within 24 hours, masked owner login, 15-minute Secure/HttpOnly/SameSite cookie sessions, same-origin/CSRF checks, bounded sessions and ten login attempts per minute. It neither generates real credentials nor supplies a general identity platform.

Five bearer/proxy tests plus a second full device-relay acceptance test exercise authority separation, denial before approval, separately approved undo, session/deployment expiry, wrong/query credentials, login rate limits, exact proxy socket peers and Host/Origin/HTTPS guards. The new browser test checks masked owner entry and absence from browser storage. The actual production entry point also starts with only synthetic bearer configuration, host `PORT` and a private `0.0.0.0` listener; no external identity fields are needed. All repairs remain synthetic.

The conventional-host profile trusts at most 16 explicit exact proxy IPs, not forwarded address headers, CIDRs, hop counts or wildcard trust. Default local/loopback behavior is retained. Real platform proxy addresses, upstream network controls and TLS routing still need verification. Static bearer is Fo's explicit credential mode, not a claim of generic MCP OAuth conformance. Token theft grants that token's bounded authority; unique high-entropy operator credentials and separate secure handoff remain necessary. SHA-256 here assumes random credentials, not human passwords. None were created or installed in a real deployment.

## Optional OAuth deployment preparation

The optional OAuth remote profile uses external OAuth access tokens for MCP, a separate cookie-bound PKCE owner flow with CSRF protection, and a distinct companion authority. It does not implement a general identity platform. Regression tests cover issuer/signature/expiry/type, exact audience, subject/client/scope separation, mixed authority rejection, query-token rejection, missing authentication, cookie/state/PKCE binding, callback replay, owner-session expiry, CSRF, host/HTTPS checks and MCP self-approval attempts. JWKS and token exchanges pin HTTPS destinations, reject redirects and bound response sizes/timeouts. Synthetic keys exist only in tests.

In device-session mode cloud owner approval/grant routes always reject; only the local device interface controls those permissions. Tests use separate real HTTP servers for gateway and companion, exercise routing and unmute plus separately approved inverses, and verify that the relay rejects arbitrary terminal/owner commands. Single delivery, duplicate-result consistency, session expiry and uncertain delivered writes are tested. The browser shows unavailable hardware when disconnected and locates approval at the companion. No network bridge starts automatically.

Remote configuration fails closed before creating a journal/listener when required identity or HTTPS fields are absent. The TLS proxy template resets forwarding headers, does not log OAuth query strings, and bounds requests. These checks simulate the approved TLS proxy boundary; no actual TLS host, external identity-provider configuration or live Fo OAuth compatibility has been validated. The default proxy must remain in the loopback network namespace, or the conventional profile must pin actual proxy socket addresses; the Node port must remain private, and production clients/scopes must follow [the deployment contract](DEPLOYMENT.md).

Diagnostics expose presence flags and constant issue messages, not environment values or error bodies. Optional fixed unauthenticated HEAD probes are separate from the opt-in paid-model smoke test. Missing credentials and proxy denials are reported explicitly; no model generation runs during startup/tests/diagnostics.

## Local repair review

The preserved baseline reproduced its passing build, 24 engine/API/MCP tests and three browser tests. A subsequent code review focused on cancellation, authorization lifetime, shutdown, transport parity, historical data disclosure and cross-client consistency. All repairs and failure injections used synthetic fixtures. This review does not establish real macOS behavior, a live Fo connection or security against an untrusted process running under the same OS user.

The cloud terminal stop initially left the old npm/tsx-launched preview holding its journal. The preview was stopped directly, long-running scripts were changed to `node --import tsx` to remove the extra tsx CLI process, and the cloud preview now runs as a directly supervised Node process. The README documents direct process supervision, and the loader is a runtime dependency so production-only installs include it. The real server lifecycle test exercises that same Node entry point.

Correctly classifying the loader as a runtime dependency exposed a low-severity advisory in the prior esbuild dependency (Windows development-server file reads, GHSA-g7r4-m6w7-qqqr). The loader was updated to tsx 4.23.15 and esbuild resolved to 0.28.2. The final production audit reports zero known vulnerabilities. The final `npm audit --omit=dev --json` result is retained in [production-audit.json](production-audit.json). That is a registry advisory check, not a complete dependency or penetration audit.

Remaining local boundaries are explicit: loopback Host/Origin checks are not authentication against another local process; the owner can edit the journal or invoke the helper directly; CoreAudio has no atomic compare-and-swap with other apps; an abruptly killed process may leave an uncertain action; audibility requires a person; and actual TLS hosting, the selected authentication configuration and Fo registration still require authorized integration checks. A valid companion bearer remains usable until provider expiry/revocation; ending one gateway session is not provider-token revocation or cancellation of an already-started write. One owner/device/process is supported; there is no tenant isolation claim. No new credentials, background agent, persistent pairing, public endpoint, outbound repair-data telemetry or account integration was introduced.
